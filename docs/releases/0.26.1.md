# HD2Runtime 0.26.1

HD2Runtime 0.26.1 is a documentation and example correctness release. It adds no gameplay mappings or
authoring features, and every 0.26.0 field, guard and baseline is unchanged.

Its purpose is to make the ModTemplate, the SDK project templates, the example projects and the beginner
docs teach the current typed API. Users had been confused by older examples, especially about weapon damage
ownership, armor-penetration fields, patch vs transaction vs plan, shared acknowledgements, and several
changes on one target.

## What is taught now

- **Damage belongs to the projectile.**
  - Use `hd2.weapon(name):attack('primary'):projectile()`, not the weapon root.
  - The weapon root owns weapon-local values such as fire rate.
  - `docs/getting-started.md` has a new "Who owns what" section covering the ownership tree:
    - weapon → attack → projectile → damage and explosion;
    - weapon → weapon-local fields;
    - magazine attachment → capacity, reload and ergonomics;
    - support weapon → backpack-owned ammo;
    - vehicle mounted weapons;
    - drop-pod slots.
- **Armor penetration is four fields**, one per impact angle: `hd2.fields.damage.ap_direct`, `ap_slight`,
  `ap_large` and `ap_extreme`.
  - Standard and durable damage are `player_standard_damage` and `player_durable_damage`.
  - `hd2.fields.damage.armor_penetration`, `standard_damage` and `durable_damage` belong to the original
    fixed JAR-5 patch. They are no longer taught anywhere.
  - Baselines differ between weapons. The AR-23 Liberator is 90 / 22 with AP 2 / 2 / 2 / 0; the AR-23C
    Liberator Concussive is 75 / 35 with AP 2 / 2 / 2 / 2.
- **patch / transaction / plan.**
  - One field is a patch.
  - Several fields of one backing object are one transaction, for example a projectile's damage and all
    four AP values.
  - Operations on different objects form a plan.
  - The guide lists the plan rules: at most 8 phases and 64 operations, one backing object per operation,
    no mixed target families in one phase, `target_from` only from an earlier phase, and at most 128
    writes per phase.
- **The SDK as the source of truth.** Take the target, constant and `expect` for the exact weapon from the
  capability JSON, the Lua stubs, the example projects, ModBuilder's Lua Preview, or `:describe()`. Never
  guess, and never copy baselines from a similar weapon.
- **Lua table pitfalls.**
  - A repeated key in one table keeps only its last value.
  - List entries need commas between tables.
  - Syntax errors appear only in `BingusSharedLoader.log`; `HD2Runtime.log` stays unchanged.

## New beginner example: LiberatorDamageTransaction

The AR-23 Liberator's projectile damage and armor penetration, as one transaction with `allow_shared=true`.
The DamageInfo record is shared with the AR-23A Liberator Carbine and StA-52 Assault Rifle.

| Field | Baseline | Value |
| --- | --- | --- |
| `player_standard_damage` | 90 | 120 |
| `player_durable_damage` | 22 | 35 |
| `ap_direct` / `ap_slight` / `ap_large` | 2 | 3 |
| `ap_extreme` | 0 | 2 |

A test compares every `expect` in this example with `currentDefault` in
`PlayerWeaponAuthoringCapabilities.json`, so stale numbers fail the release.

## Examples changed

| Example | Change |
| --- | --- |
| **Jar5AP4** | Rewritten from the legacy `:projectile():damage()` / `armor_penetration` form to the typed projectile transaction (`ap_direct`, `ap_slight`, `ap_large` 3 → 4, `allow_shared`). It writes the same bytes as the original gameplay-proven patch. |
| **FireModeSelect** | Rewritten from the older `weapon.default_fire_mode` / `hd2.enums.fire_mode` form to `hd2.fields.fire_mode.modes`. The Concussive's `{automatic, single}` becomes `{single, automatic}`, making Semi Auto the default. Now requires 0.26.0. |
| **OrbitalLaserProof** | **Was broken:** its beam DamageInfo is a shared write and the example lacked `allow_shared=true`, so it was rejected. Fixed. |
| **ShieldRelay** | Removed. It used the fixed-resource Shield Relay transaction; ShieldRelayRecreation is the typed replacement. |
| **ReadKnownValues** | Removed. It used the legacy read-only `hd2.observe` with the short-name catalog (`'Bastion'`, `'AMR'`). Use the capability files and `:describe()` to inspect fields. |
| **LiberatorDamageTransaction** | New. |
| **ModTemplate** | Still the Concussive fire-rate patch, now with a pointer to projectile-owned damage. |
| **Minimum versions** | 25 examples declared a floor below 0.23.2 (as low as 0.14.1), but typed writes can fail in game on 0.23.0 and 0.23.1 (see `0.23.2.md`). They now require **0.23.2**. Examples that need later features keep their later floor. |
| **IDE files** | Every example now ships `.luarc.json` (stub completion) and `.gitignore`. |

**SDK project templates** (`hd2.py new --template`):
- `fire_rate` is the default, identical to the ModTemplate.
- `projectile_damage` is the Liberator transaction.
- The legacy `jar5`, `shield` and `observer` templates are removed.

## Clearer metadata and errors

- **Constants in the catalog.** `PlayerWeaponAuthoringCapabilities.json` now lists each field's Lua constant
  in `apiFieldConstant` (all 3,814 resolve to their field IDs). Users no longer have to search the stubs,
  where `standard_damage` and `player_standard_damage` both appear.
- **Stub labels.** The Lua stubs label the legacy fixed-resource constants as legacy, and name their typed
  replacements.
- **Error message.** Using `armor_penetration`, `standard_damage` or `durable_damage` on a typed weapon target
  now says it is a legacy field and names the typed fields, instead of "projectile objects only accept
  projectile or linked damage fields". Behavior is unchanged: the write is still rejected.
- **Historical banners.** `guarded-patch.md` and `transaction-ensure.md` are marked as historical documents
  of the original fixed-resource API, each pointing to its typed equivalent.

The runtime still accepts the legacy fixed-resource API, so old mods keep working. It is only no longer
taught.

## Validation

New: **`scripts/validate_examples.py`**, run by the release build (a failure stops the release) and by
`tests/test_examples.py`. It checks 46 examples: 43 example projects, the live options test, the ModTemplate,
and the two SDK templates. For each one it:

1. rejects legacy API usage (legacy constants, `:projectile():damage()`, `hd2.observe`, the old fire-mode
   enum);
2. runs the addon against the current API through a validating adapter, so every patch, transaction, plan and
   ensure is validated by the production write domains (fields, target paths, `expect` baselines, required
   acknowledgements, and one target family per plan phase);
3. requires `min_version` to be at least the oldest runtime that has every API the example uses;
4. prepares every operation against the retained snapshot, and requires the live bytes to equal `expect`.
   Nothing is written.

Mutation checks confirm it fails an example with a stale baseline, a legacy constant, or a missing
`allow_shared`.

**Packaged runtime.** Every example project now runs from the built runtime ZIP, either as a named scenario
or as an automatic `example-<name>` scenario. That makes **57 scenarios**, up from 36. Every ensure applies,
verifies, and re-applies after a simulated reset.
