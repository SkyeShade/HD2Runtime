# HD2Runtime 0.25.0

HD2Runtime 0.25.0 traces Booster implementation natively, resolves the last support-equipment
call-in relationships, and adds in-game options bound to ensured operations. In-game options are
confirmed in game. Ownership and writability still come only from native structure, and ambiguous
values stay read-only.

## In-game options (confirmed in game)

`hd2.options({id, title})` declares a page of toggles, sliders and choices on the **MODS** tab
added by CowboyBingus **Mod Options Menu** v1+ (api 1). A slider or choice handle can be passed as
a field `value` in `hd2.ensure`, and a toggle as its `enabled`. Changes take effect when the
player presses APPLY: the same ensure re-runs the full guarded path, with the same target,
acknowledgements and conflict checks. Disabling restores the reviewed baseline through the same
guards. See [in-game options](../options.md).

```lua
local options=hd2.options({id='liberator_damage',title='Liberator Damage'})
local enabled=options:toggle({id='enabled',label='Enabled',default=true})
local damage=options:slider({id='damage',label='AR-23 Liberator Damage',min=90,max=500,step=10,default=150})
return hd2.ensure({enabled=enabled,patch={id='liberator-damage',allow_shared=true,
    target=hd2.weapon('AR-23 Liberator'):attack('primary'):projectile(),
    field=hd2.fields.damage.player_standard_damage,expect=90,value=damage}})
```

- **Bound values are owned by `hd2.ensure` only.** `hd2.patch`, `hd2.transaction` and `hd2.plan`
  reject option handles. `expect` stays the reviewed baseline and never follows an option.
- **The whole option domain is validated when the ensure is declared:** a slider's minimum,
  maximum, default and first step, or every choice value, plus the restore request. A slider
  outside a field's safe range, a fractional slider on an integer field, a read-only field, or a
  missing acknowledgement fails at startup, not in game.
- **Changes are debounced by 0.5 s.** An in-flight resolution is cancelled; this is safe because
  guarded writes never yield. A no-op APPLY does no work.
- **Owned transitions.** A live value equal to the bytes this same ensure verified last time is
  accepted as its own. Any other value is still a `CONFLICT`. The rule lives in
  `core/ownership.lua` and is shared by all five typed write domains.
- **Disable** restores the baseline, then the ensure is dormant: no checks and no writes, even
  after a game reset. Re-enabling runs a full guarded resolution.

### Mod Options Menu is an optional dependency

HD2Runtime itself still needs only Bingus Shared Loader v15+ / API 1. Mod Options Menu, which
needs Bingus Shared Loader v18+, is an optional dependency of mods that call `hd2.options`, and
of those mods only.

- Mods that do not call `hd2.options` are unchanged: no probing, no scheduler work, no log lines.
- Without the menu, or with an incompatible one, each options page logs **one warning** and every
  `hd2.ensure` bound to it stays **inactive for the session** (status `unavailable`). Defaults are
  never applied silently. Operations not bound to options run normally, in the same mod and in
  other mods.
  ```
  [HD2Runtime] options liberator_damage unavailable: Mod Options Menu is not installed; configurable operation will not be applied (liberator-damage)
  ```
- Availability is decided once per session. An absent menu gets a 5 s grace period, because it may
  load after the mod. A rejected, failing, disappearing or duplicate registration affects only the
  options involved and is not retried.
- Declare the dependency in `hd2runtime.json`, beside the unchanged `requires` block. The SDK and
  starter builders validate it and mention it in the manager description; it never gates loading.
  ```json
  "optional": {"mod_options_menu": {"min_version": "1.0.0", "api": 1, "bingus_min_release": 18}}
  ```

### Live confirmation

Confirmed in game with HD2Runtime 0.25.0, Mod Options Menu v1.0.1 and Bingus Shared Loader v18 on
Steam build 25480438. The test used the live-validation mod `examples/live/HD2RuntimeOptionsTest`
(AR-23 Liberator `player_standard_damage`, expected 90).

- The option controls appear on the MODS tab and work.
- APPLY updates the value managed by the runtime.
- Disabling restores the reviewed baseline.
- Without Mod Options Menu, only the option-bound operation is disabled.
- Saved values survive a full game restart. A saved value of 230 was loaded and applied at
  startup.

## Boosters

The research reads the unpacked `game.dll` image from the retained snapshot (the on-disk DLL is
packed) and traces each booster through the code that implements it. See
[booster authoring](../booster-authoring.md).

- **Identity:** all **20 boosters resolve uniquely** (0.24.0: 7 unique, 11 candidate sets, 2 by
  inference). `game.dll`'s own Booster enum-name table is value-indexed and agrees with the type
  library's alias lengths for all 22 values.
- **Coverage:** **19 of 20 boosters are writable** (0.24.0: 2), with **42 field instances**
  (0.24.0: 5).
- **Hellpod Space Optimization stays blocked.** Its effect is a conditional select with no scalar,
  and its table scalar is never read by game code.

| Target | What it writes | Fields | Acknowledgement |
| --- | --- | --- | --- |
| `booster:tuning()` | Scalars in the native Booster definition table (Vitality 0.9, Stamina 1.3, Muscle 0.35, UAV 1.5, reinforcement budget +1 and 0.75, Localization 0.9, Extraction 0.7, Motivational Shocks 0.5, Sample Scanner 0.15, Dead Sprint health floor 0.05, Sample Extricator cap 10, Integrated Extinguishers 0.5), range-checked | 13 | `allow_unverified_effect` |
| `booster:explosion()` | Hellpod-impact explosions and their DamageInfo: Firebomb Hellpods, Stun Pods, Concealed Insertion (smoke) | 21 | `allow_unverified_effect`, `allow_shared` |
| `booster:status_damage()` | Dead Sprint drain (status 59) damage | 2 | `allow_unverified_effect`, `allow_shared` |
| `booster:granted_stratagem()` | Surplus EAT Allocation uses | 1 | `allow_unverified_effect` |

| `booster:deployed_entity()` | Armed Resupply Pods turret (unchanged from 0.24.0) | 2 | `allow_unverified_effect` |

- New field constants in `hd2.fields.booster`: `damage_taken_scale`, `stamina_scale`,
  `slow_scale`, `radar_range_scale`, `reinforcements_per_player`,
  `reinforcement_cooldown_scale`, `encounter_rate_scale`, `extraction_time_scale`,
  `terrain_slowdown_scale`, `double_sample_chance`, `health_floor`, `sample_drop_cap` and
  `burn_decay_bonus`.
- **Only data is written; executable code never is.** Every write re-proves live the build
  fingerprint, `SizeOfImage`, the relocated enum-name table and target name, every table row's
  identity, and the exact bytes of `IsBoosterActive` and each pinned gate, selector and consumer
  instruction.
- **No booster edit is gameplay-proven yet**, so every booster write still requires
  `allow_unverified_effect`. The native value and its consumer are proven; the in-game effect of a
  changed value is not.

## Support equipment

- **B/MD C4 Pack** now links to its call-in. The research joins two native loadout identities
  (`LoadoutEntryComponent` item id and `LoadoutPackageComponent` package) against the live
  StratagemDefinition table. The placed charge links only because both hold: its loadout item id
  is the C4 call-in id, and the call-in package is its own package. The call-in rack attaches the
  detonator and the backpack, and the backpack's deposit refills the detonator.
- **SG-88 Break-Action Shotgun and CQC-72 Entrenchment Tool** are published as `no_call_in` (world
  pickups), not `unresolved`. No StratagemDefinition carries their item ids or names their
  packages.
- Known call-in links: 32 → 33; unresolved: 3 → 0. A loadout id alone never creates a link.
- Write guards are unchanged. All 970 support field instances are identical to 0.24.0, and CQC-72
  stays blocked.

## API and SDK

- `hd2.options`, with `:toggle`, `:slider` and `:choice` handles (`:get`, `:index`, `:describe`,
  `:available`). New `hd2.ensure` watch statuses: `waiting_for_options`, `unavailable`,
  `blocked` and `disabled`.
- `hd2.booster(name)` gains `:tuning()`, `:explosion()`, `:status_damage()` and
  `:granted_stratagem()`.
- New docs: `docs/options.md`. `docs/booster-authoring.md` is rewritten for the native model.
- New example projects, each requiring 0.25.0: `BoosterTuning`, `IncendiaryHellpods` and
  `LiberatorDamageOptions`. The ModTemplate now requires 0.25.0.
- The SDK generator now reads source docs as UTF-8. Earlier SDK ZIPs showed some punctuation in
  `booster-authoring.md`, `options.md`, `getting-started.md` and
  `attachment-preset-research.md` as garbled characters.

## Validation

- `scripts/validate_options_binding_snapshot.py` runs Mod Options Menu's own source against the
  retained snapshot with a copy-on-write overlay (32 checks). It covers saved, malformed and
  out-of-range values; live, no-op and rapid changes; owned transitions; drift;
  disable/restore/re-enable; a reset while disabled; a pending retry; conflicts; transactions,
  plans and every guard.
- The Booster snapshot validator performs a real overlay write, read-back and rollback for all 42
  fields. It rejects conflicts, missing acknowledgements, out-of-range values, changed instruction
  bytes, changed enum names, changed row identities, a relocated module and a wrong build.
- The packaged-runtime validator applies **19 scenarios** from the built runtime ZIP (0.24.0: 12).
  New scenarios:
  - `booster-tuning`, `booster-explosion` and `booster-coverage`;
  - `options-live` and `options-missing`;
  - `options-test-mod-live` and `options-test-mod-missing`, which run the in-game test mod itself.
