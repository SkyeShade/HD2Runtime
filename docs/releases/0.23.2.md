# HD2Runtime 0.23.2

HD2Runtime 0.23.2 is a critical runtime hotfix for how modules are loaded at startup.
Everyone on 0.23.0 or 0.23.1 should update. It makes no API, field, or metadata
changes.

## The problem in 0.23.0 and 0.23.1

Typed writes could fail in game once startup was over. This affected player
weapons, support weapons, stratagems, vehicles, backpacks, and magazine
attachments. Patches, transactions, plans, and ensures were all rejected before
anything was written:

```
[HD2Runtime] patch <id> REJECTED code=VALIDATION_FAILED reason=hd2runtime/domains/player_weapon_writes.lua:339:
module 'hd2runtime/core/fingerprint' not found
```

- **The module files were in the ZIP.** Every module the runtime references is
  present in the published 0.23.0 and 0.23.1 runtime ZIPs, under the right name.
  This was not missing packaging and not a stale `require` path.
- **The cause was how long module lookup works.** The game engine can find the
  runtime's Lua files only while its startup package is loaded. Bingus Shared
  Loader passes `require` straight to the engine. Modules loaded during startup
  kept working. A module required for the first time later could no longer be
  found.
- **Why it started in 0.23.0.** The performance work moved the build fingerprint
  check into a new shared module, `hd2runtime/core/fingerprint`. That module is
  first required when a write is applied, about 3 seconds after startup, which
  is too late.
- **Why tests missed it.** The source-tree tests preload every module up front,
  which hides this failure mode.

## The fix

- At startup, the runtime now captures every shipped module into
  `package.preload`, using a module list generated when the package is built.
  Capturing stores each module's loader without running it, so modules still run
  only when first used. Any later `require` resolves safely, including at apply
  time and when an ensure re-applies after drift.
- If any shipped module cannot be found, the runtime fails at startup with a
  clear error. It no longer fails later in the middle of an operation.

## Validation against the built runtime ZIP

`scripts/validate_packaged_runtime.py` validates the built runtime ZIP itself,
not the source tree. The release build now runs it and stops if it fails.

- **Static check.** Every internal module name referenced by shipped Lua must
  resolve inside the archive.
- **Game Lua runtime.** The archive runs on the game's own `lua51.dll`, behind an
  emulated Bingus loader.
- **Simulated lookup failure.** Module lookups from the archive work only during
  startup and fail afterwards, as in game.
- **Nine write scenarios**, applied against the retained current-build snapshot
  through a copy-on-write memory overlay. No game process is touched and nothing
  is really written:
  - player weapon patch;
  - the GUI-generated player weapon transaction and patch;
  - support weapon;
  - stratagem;
  - vehicle armor;
  - vehicle mount swap;
  - backpack;
  - Shield Relay;
  - magazine attachment.
- **Reset check.** Every ensure must re-apply after a simulated game reset, with
  late lookups still disabled.

A negative-control test runs the same check with the 0.23.1 library entry and
reproduces the exact in-game error.

## Fingerprint cache

The build-fingerprint cache is unchanged and remains tiny and in-memory. It holds
one short key per successful match: run mode plus the base address and handle of
the executable and of game.dll. Hashing streams each file through one 1 MiB
buffer. No executable, DLL, or snapshot contents are kept in memory or written to
disk, and mismatches are never cached. In validation, the executable and game.dll
are each hashed once per process, including through re-apply after reset.

## Upgrading

- **Players:** replace HD2Runtime 0.23.0 or 0.23.1 with
  `HD2Runtime-0.23.2-runtime.zip` in your mod manager, purge and redeploy, then
  restart the game.
- **Mods:** existing mods need no changes. The ModTemplate now requires 0.23.2.
- **Authors of multi-file mods:** `require` your own extra files at the top of
  `addon.lua`. The same startup-only lookup applies to gameplay mod resources.
