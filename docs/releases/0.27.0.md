# HD2Runtime 0.27.0 — Automatic Asset Loading

A reference swap is only as good as the assets behind it. Before 0.27.0, the swaps below wrote a valid
reference, but the replacement showed up broken unless some player happened to equip the donor item:

- an EAT-700 put into a Stalwart pod spawned as a purple, non-interactable question mark;
- a Reprimand firing Talon projectiles fired invisible, broken shots.

HD2Runtime 0.27.0 fixes this. When a swap points at an item nobody carries, Runtime loads that item's package
through Helldivers 2's own package loader, waits until the engine reports it resident, and only then writes
the reference. The donor item no longer needs to be in the mission or anyone's loadout. Mod authors change
nothing and never see a package ID.

This is also the first public release since 0.26.0. It includes the unpublished 0.26.1 work and throwable
authoring (see [Also in this release](#also-in-this-release)).

## How it works

- **Automatic package dependency discovery.** A validated patch, transaction or plan records which packages
  its new references need:
  - a pod slot that receives a pickup;
  - a vehicle mount that receives another vehicle's mounted weapon;
  - a projectile or explosion reference taken from another weapon.

  The catalog maps semantic objects to the package that owns their resources: 331 objects, 260 with a
  structurally proven package and 71 unknown. It is generated from the build's own data and never infers a
  dependency transitively. Same-package swaps and vanilla values need nothing.
- **Native package loading through HD2's own loader.** Items are loaded when some system holds a reference on
  their generated loadout package in game.dll's reference-counted package system. The game takes these
  references for loadouts on the ship, mission preparation, hot-joining players and armory previews. Runtime
  takes its reference through the same function, once per package per session. It re-proves every native
  call first:
  - the build fingerprint;
  - the exact code bytes of the request and release functions, and of the engine's `has_loaded` and
    package-lookup functions;
  - the reference-map instance, which must be under 75% full.
- **Asynchronous wait before the write.** The operation's status is `waiting_for_assets` while the engine
  loads the package. Runtime polls the engine's package list and part states every 0.25 s, never blocking the
  game, and the normal guarded write runs once every part is loaded. A package requested by several operations
  is requested only once.
- **`ASSET_UNAVAILABLE` safe failure.** The write is rejected and the vanilla reference stays in place if:
  - the package is not resident after 90 s;
  - a proof fails;
  - the session budget of 64 packages is spent;
  - the runtime cannot request packages.

  For a known dependency, Runtime never writes a reference to assets it could not confirm resident.
- **Retention.** Runtime keeps its references for the session and never unloads. Spawned pods, fired
  projectiles and vehicles already on the map use the assets without holding references, so Runtime cannot
  prove a package is unused. Packages the game itself referenced are never touched.

## API

Most mods need nothing new: `hd2.patch`, `hd2.transaction`, `hd2.plan` and `hd2.ensure` load dependencies
automatically.

- **`hd2.require_assets({id=..., target=... | targets={...}})`** optionally warms packages up front, so later
  writes apply without waiting. It takes 1 to 16 typed handles: pickups, weapons, support weapons,
  throwables, vehicles, backpacks, mounted-weapon candidates and projectile handles. Its status goes from
  `waiting_for_assets` to `complete` (`result.status` `RESIDENT`), or to `rejected` with `ASSET_UNAVAILABLE`.
- **`hd2.asset_dependency(target)`** is offline metadata for tools: whether a typed handle's package
  dependency is known and auto-loadable, how it was derived, the package's short name, and whether it was
  live-tested.

There is deliberately no `hd2.load_package(id)`. Package identities come only from the generated catalog,
are checked against the build's bundle database, and never come from callers.

## SDK metadata

- **`sdk/AssetDependencyCapabilities.json`** (contract `hd2runtime.asset_dependencies.v1`) publishes a
  `packageDependency` entry for each of the 331 semantic objects:
  - `known`, `autoLoadSupported` and `derivation`;
  - `package` (short name) and `packageNamed`;
  - `liveTested` and `packageLiveLoaded`;
  - `blocker`.

  It also publishes `referenceFamilies` (the proof level per reference family) and `liveEvidence`. It
  contains no package or resource hashes.
- 24 packages are proven by their identity in the build, but their names have not been recovered. They load
  the same way; the metadata marks them `packageNamed=false`.
- `sdk/metadata.json`, the Lua stubs and `docs/api.md` gain the two new functions.

## Integration

- **Projectile swaps.** A projectile or explosion reference taken from a weapon in another package loads that
  weapon's package first. LAS-58 Talon was previously blocked as a projectile source
  (`SOURCE_WEAPON_REQUIRED`) because its only observed failure was missing assets; it is now accepted and
  loads `laser_pistol`. In the projectile composition catalogs:
  - 66 source attacks are `PACKAGE_AUTO_LOADED`;
  - 1 (GP-31) is `DEPENDENCY_UNRESOLVED`;
  - the pre-0.27 observation is kept in `observedWithoutLoader`.

  A source observed to need its own package whose package is unknown stays rejected. The approved
  compatibility classes are unchanged.
- **Pod payloads.** A non-vanilla pickup's package loads before the slot is written. Each pickup in
  `PodPayloadCapabilities.json` publishes `packageDependency`:
  - 63 are `LIVE_PROVEN`;
  - the Supply Box is `ALWAYS_RESIDENT`;
  - 4 are `UNRESOLVED`.

  The two tested rack/pickup combinations are published as `liveVerifiedPairs`.
- **Vehicle mounts.** A mounted weapon from another vehicle's package loads before the mount is written. The
  vehicle metadata's warning no longer says packages are never loaded.

## Package residency and slot compatibility are separate

Package loading answers one question: are the replacement's assets loaded? It says nothing about whether the
game behaves correctly with that reference in that slot. Each domain keeps its own evidence and
acknowledgements for that, unchanged:

| Family | Package residency | Slot / gameplay compatibility |
| --- | --- | --- |
| Pod-payload pickup | **Live-proven** | Unverified in general: `allow_unverified_reference` is still required |
| Projectile reference | **Live-proven** | Unchanged: only approved compatibility classes can be swapped |
| Explosion reference | Offline-proven; same loader path and source-weapon packages as projectiles | Unchanged |
| Vehicle mount | Offline-proven | Unverified: `allow_unverified_reference` is still required |

A reference whose package is unknown gets no automatic load. It behaves as it did before 0.27.0, gated by
the same acknowledgement.

## Live results

All tests ran in game on build F5FEE03DCFDB, with **nobody carrying the donor item**. The evidence is in
`research/package-residency-live-evidence.json`.

| Test | Result |
| --- | --- |
| Stalwart pod → EAT-700 | **Pass.** The pod spawned a real, usable EAT-700 instead of the purple question mark. This is the original bug. |
| Reprimand → Talon projectile | **Pass.** The Reprimand fired the Talon projectile with correct visuals and function. |
| MG-43 pod → Grenade Box | **Pass.** The Grenade Box spawned correctly and could be picked up. |
| FRV → Bastion cannon | **Inconclusive.** The Pelican did not deliver the FRV, so the mount was never observed. This is not evidence for or against package loading. Gameplay compatibility of a Bastion cannon on an FRV remains unverified. |

The four test mods ship as example projects: `AssetTestStalwartPodEat700`,
`AssetTestReprimandTalonProjectile`, `AssetTestMg43PodGrenadeBox` and `AssetTestFrvBastionCannon`.

## Known limitations / caveats

- **Multiplayer and unmodded clients.** Loading is local. A host with the mod loads the package for itself
  only. A client without the mod resolves what its own game loaded and may still see a missing asset.
  Runtime makes no claim about remote clients. This has not been live-tested.
- **Vehicle mounts** are not live-tested for asset loading, and mounted-weapon swaps remain unverified for
  gameplay.
- **Explosion references** from another weapon's package use the live-proven loader path but were not tested
  separately.
- **Unknown dependencies.** 71 catalog objects have no provable package and get no automatic load. 59 are
  mounted weapons, mostly enemy or unnamed; the rest are the Supply Box, the four pod items above, and a few
  weapon variants (for example the LAS-7 Dagger and the GP-31 Grenade Pistol).
- **Game updates.** After a Helldivers 2 patch the loader's code-byte proofs fail. Swaps that need another
  package are then rejected with `ASSET_UNAVAILABLE` until `scripts/research_package_residency.py` is re-run
  on the new build. Writes without a package dependency are unaffected. See `docs/game-update-migration.md`.

## Validation

- **Unit suite:** 431 tests.
- **Generator freshness:** every domain table and SDK file checks as current. New steps are
  `apply_projectile_residency` and `generate_package_residency`.
- **Snapshot validation** (`scripts/validate_asset_residency_snapshot.py`), against all three retained
  snapshots:
  - the loader proofs on real memory;
  - resident, mid-load and absent package states;
  - rejection of changed code bytes, a wrong build, uncatalogued packages, a runtime without native loading,
    and a spent budget;
  - deduplication (two operations, one native request);
  - bookkeeping-only release;
  - the 90 s timeout.
- **Examples:** 54 of 54 pass `scripts/validate_examples.py`.
- **Packaged runtime:** 65 scenarios run from the built runtime ZIP, with late module lookups disabled and a
  simulated engine loader. The asset scenarios request their package once, wait, then apply.
