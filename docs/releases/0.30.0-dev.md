# HD2Runtime 0.30.0-dev (development line; not released)

The custom stratagem system becomes the 0.30 development line. This pass is stabilization: a lobby-correct carrier
allocator, a startup progress display, quieter logs and a builder-facing schema. No new payload family. Nothing is
tagged or released.

## Versions

- `VERSION` is `0.30.0-dev`. The startup line reads `HD2Runtime 0.30.0-dev initialized (API 1)`, and the artifacts are
  `HD2Runtime-0.30.0-dev-runtime.zip`, `-sdk.zip` and `HD2Runtime-ModTemplate-0.30.0-dev.zip`.
- `hd2.version` stays a compatibility version, `0.30.0` (MAJOR.MINOR.PATCH). Mods built by an SDK before 0.28 parse
  nothing else, so every exported mod keeps loading. `hd2.version_label` is `0.30.0-dev`.
- SemVer: `0.30.0-dev` is below `0.30.0`. A mod requiring `0.30.0-dev` loads on this build and on the 0.30.0 release.
- The custom stratagem examples require `0.30.0-dev` (the API is not in 0.28.0): PelicanCasExample 0.1.7,
  GasBarrageExample 0.1.6, GasEatExample 0.1.6, HmgSentryExample 0.2.1 and EagleStunRocketPodsExample 0.3.1
  (`DEV LINE BUILD`). The examples themselves are unchanged.

The Pelican is the advanced example. Every write stays instance-local and solo-host only, and unsupported fields
keep refusing. See `docs/custom-stratagem-api.md`.

## Multiplayer allocator (experimental; missions still refuse)

- Carriers are mapped by custom stratagem id across the lobby. Every peer allocates every registered id.
- Candidates are ranked deterministically.
- Native selections (the saved loadout plus every peer record) are excluded for everybody.
- The same id reuses its reservation; another id finds it taken.
- Nothing depends on join, iteration or player order.
- Call state stays per call.
- Tests cover 2 and 4 players on one id, different ids, a natively selected carrier, reuse versus another id, and every
  shuffled order.
- The table "What this machine can see of the lobby" in the API doc records what is visible.

## Experimental multiplayer test build

This is a live-test build, not a claim that multiplayer is safe. Logged once: `CUSTOM STRATAGEMS MULTIPLAYER
EXPERIMENTAL`.
- The selector's `NOT_SOLO` refusal is removed: custom stratagems can be selected in a lobby. The write is this
  machine's own loadout record.
- With several players the host runs its own custom calls. The solo guards of those writes accept only a custom
  stratagem call's own writes. A client refuses its own calls: every custom write stays host-only.
- No Runtime networking. Diagnostics: `CUSTOM MP PEERS / LOBBY / CARRIERS / PICKS / CALL / DESYNC / RECORD`.
- See docs/custom-stratagem-api.md, "Several players".

## Builder schema and project format

- `sdk/CustomStratagemSchema.json`: the fields, units, ranges, defaults, support status and donor catalogues,
  generated from the Runtime's own limits.
- `sdk/schemas/custom_stratagems.project.schema.json`: the project file's JSON Schema.
- `hd2.py custom-stratagem validate|compile`: `custom_stratagems.json` compiled to `src/addon.lua`. `hd2.py build`

- `build/build-report.json` beside the ZIP: the artifact's SHA-256 and each icon's source digest.
- The data examples are fixtures that register exactly as the hand-written examples do.

## Expendable custom stratagems: carrier weapon clones (2026-10-05, not live-tested)

- **The family.** A new payload family, `delivery={family='expendable', weapon, presentation, modify, level}`
  (`docs/custom-stratagem-api.md`). It delivers a mission-scoped clone of the donor weapon (today the EAT-17) on an
  unused carrier weapon of its expendable class (the EAT-700, then the EAT-411).
- **The clone.** The carrier weapon's own type records become the donor's at mission start, before it exists:
  presentation, model, animations, round, sounds and handling, from the pinned research values. Its pod row presents
  as the custom stratagem. Everything is restored byte for byte aboard the ship. The donor is only ever read.
- **Availability.** While every carrier weapon is a lobby member's native pick or another custom stratagem's, the
  definition is unavailable: its panel tile warns, picking it is refused, and a picked one unpicks itself (its slot is
  plainly the token). Re-evaluated aboard the ship and frozen at mission start.
- **Several players.** Every compatible Runtime converts the same carrier weapon. The carrier map hash input names it
  for expendable entries only. hd2rt/1 and every other definition's hash are unchanged.
- **Example:** `proof/EAT17GExample` 0.1.0 (`EAT-17G CLONE BUILD`), with the clone level as a Mod Options choice for
  staged live tests.
- **Research:** `research/docs/carrier-weapon-clone-F5FEE03DCFDB.md`. It includes the pickup prompt icon consumer
  proof.
- **Validation:** `scripts/validate_weapon_clone_snapshot.py` passes on all seven snapshots.

## Projectile homing (2026-10-06, not live-tested)

`hd2.projectiles.homing(weapon, {target = 'enemy' | 'friendly', turn_rate, cone, range, ...})` makes the local
player's own shots of a weapon turn toward a living enemy, or another player's Helldiver, in flight
(`docs/projectile-homing.md`).

- **What is written.** Each update, one guarded write of that shot's own velocity: the flight record +0x0C, turned by at
  most `turn_rate` x dt at the same speed. The weapon, its projectile row and every other projectile are never written.
  The research (`research/projectile-homing-F5FEE03DCFDB.json`) proves that the projectile update integrates and
  hit-tests each step from exactly that vector.
- **Which weapons.** 173 named owners of a projectile type in the projectile identities research
  (`hd2.projectiles.homing_list()`):
  - player, underbarrel, support and vehicle weapons;
  - mounted weapons;
  - sentries and emplacements;
  - Eagle and orbital payloads.

  Only shots fired by the weapon's own entity types and credited to the local player are steered.
- **Several players** need `multiplayer = true` (experimental). Each machine steers only its own player's shots. Other
  machines draw them flying straight, with the hit where they homed (the game's impact message carries the shooter's
  impact position).
- **Validation.** `validation/projectile-homing-snapshot.json`: on the retained mission snapshot a planted R-36 Eruptor
  shot locks on a living enemy and turns 1.5 degrees per 1/60 s update at 90 degrees per second, at the same speed. It
  converges in 12 guarded writes with no protection change. Live test: `examples/projects/ProjectileHomingTest`
  (live evidence family `projectile_homing`, pending).

## Enemy spawn weights (2026-10-06, not live-tested)

`hd2.enemies.spawn_weight(enemy, multiplier, {allow_unverified_effect = true})` changes how often an enemy type
spawns (`docs/enemy-spawns.md`).

- **The rosters.** game.dll keeps one static enemy roster per faction (Terminids 45 rows, Illuminate 46, Automatons 61):
  each row is an enemy type in a spawn group with ten weights, one per difficulty.
- **The pick.** Every spawn that picks an enemy type (14 call sites) goes through the game's own `PickEnemy`: within
  the group, weight / sum at the mission difficulty. Research: `research/enemy-spawn-weights-F5FEE03DCFDB.json`.
- **What a multiplier does.** It writes that type's weights as vanilla × k:
  - **0**: never picked.
  - **k > 1**: more of it within the groups it shares, and fewer of the others. Its total count is unchanged where it
    is alone in a group.
  - **How many enemies a spawn makes is not changed.** That is each spawn system's template counts, which are not
    written yet.
- **What loads.** A mission loads the packages of the types whose weight is above 0, so a weight never goes from 0 to
  positive during a mission: such a restore waits for the ship.
- **Host.** The host's rosters decide. On a client the setting does nothing.
- **Validation.** `validation/enemy-spawn-weights-snapshot.json`; live test `examples/projects/EnemySpawnMixTest` (live
  evidence family `enemy_spawn_weights`, pending).

## Weapon variants and Runtime-owned custom models (2026-10-06, not live-tested)

A custom stratagem can now deliver a custom version of a support weapon whose component class is itself.

- **The weapon family.** `delivery={family='weapon', weapon, round, model, model_use, presentation}`, carrier group
  `weapon` (docs/custom-stratagem-api.md; research research/docs/weapon-variants-F5FEE03DCFDB.md).
  - Today the only such weapon is the M-1000 Maxigun. Its own type becomes the variant for one mission: its name and
    icon, its round (a catalogued output of its own class: the LAS-58 Talon's) and its model.
  - Its own stratagem and pod carry it, and everything is restored aboard the ship.
- **Custom models.** `hd2.resources.model(id)` and `models/<id>.json` (docs/custom-models.md).
  - The SDK build derives the mod's own unit, body material and colour table from the base weapon's unit in the
    installed game.
  - It ships them as a patch of the base's package archive, beside the vanilla model, which is never replaced.
  - The Runtime names the unit only when it is loaded and exact, and after the UnitPath consumer review re-proves on
    the running game.dll.
- **No fallback** (the user's rule). A native pick of the Maxigun makes the variant unavailable, and a selected variant
  blocks the Maxigun.
  - The EAT pool's regular EAT-17 (the donor itself) is now reserved like every carrier weapon. A native EAT-17 pick
    takes it, and as the last viable carrier it is blocked.
- **The example.** proof/LaserMaxigunExample 0.1.0, the LAS-1000 Laser Maxigun: Talon rounds and a debug model (the
  Maxigun's mesh with one bright colour per material zone). Mod Options switches between check only and the debug
  model.
- **Validation.** Every retained snapshot (scripts/validate_weapon_variant_snapshot.py), the packaged scenario
  example-laser-maxigun, and tests/test_weapon_variants.py.

## Building examples and mods from the downloads (GitHub issue #2)

- **The report.** An example built from inside the extracted SDK failed with wrong paths: its `hd2runtime.json` still
  had the repository's `../../../sdk`. A double-clicked build closed before its error could be read.
- **`build.py`.** Every example and every new SDK project uses one template, `sdk/templates/build.py`. It finds the
  SDK itself, in this order:
  - the `HD2RUNTIME_SDK` environment variable;
  - the configured `sdk` path;
  - the project's folder or any folder above it that is the SDK, or a subfolder of one named `sdk` or ending in
    `-sdk`.

  Without an SDK it says what to do, with no traceback. Started by a double-click, it waits for Enter.
- **The example-projects ZIP.** Each example's `sdk` path points at the SDK ZIP extracted beside it. The ZIP's README
  explains that layout.

## Before 0.30.0: custom projectiles in multiplayer (RELEASE BLOCKER)

Runtime-owned custom projectiles (`docs/custom-projectile-rows.md`; `hd2.actions` custom projectile spawns, weapon
projectile replacement, the Pelican gun's rounds) exist only on the machine that spawns them. They are spawned through
SpawnProjectile on that machine's pool, so other players never see them, and every path is host- and solo-guarded.
This must be handled before 0.30.0 is released.

The direction found so far is to change each machine's own copy of a shot in flight instead of spawning a new one.
- Each machine simulates its own copy, and the shooter's impact message makes the others explode their copy at the
  shooter's impact position (research/projectile-homing proof 8).
- So every compatible Runtime would convert its own copy of the same shot. The Gas EAT and native barrage provenance
  pattern already does this for impact explosions.

Not designed or implemented yet. Coordinate with the custom projectile and Pelican work before starting.
