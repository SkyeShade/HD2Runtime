# HD2Runtime 0.24.0

HD2Runtime 0.24.0 expands support-weapon authoring and adds Booster authoring as a new domain.
Scraped wiki data is used only to fingerprint and cross-check native values; ownership and
writability always come from native structure. Ambiguous values stay read-only.

## Support weapons

Support-weapon authoring grows from **27 weapons / 828** published writable-field mappings to
**31 weapons / 970**. Every field is validated on the retained snapshot as a guarded no-op. See
[support-weapon authoring](../support-weapon-api.md).

### New writable field families

| Field | Native owner | Where writable | Acknowledgement |
| --- | --- | --- | --- |
| `reload.duration` | `WeaponReloadComponentData` | 14 weapons with a non-zero native duration | `allow_unverified_effect` |
| `projectile.lifetime` | `ProjectileInfo` | LAS-99, PLAS-45, RL-77, RS-422, S-11 | `allow_shared` (shared definition) |
| `projectile.penetration_slowdown` | `ProjectileInfo` | Every resolved projectile branch | `allow_shared` (shared definition) |
| `windup.wind_up_seconds` | `WeaponWindUpComponentData` | M-1000 Maxigun | none (exact match) |
| `windup.wind_down_seconds` | `WeaponWindUpComponentData` | M-1000 Maxigun | `allow_unverified_effect` |

- The type library's member-name lengths identify each field. Scraped values confirm it: 5/5
  lifetimes and 27/27 penetration slowdowns match, and the Maxigun's 0.5 s spin-up matches.
  Filediver labels a different offset as the lifetime; both lines of evidence contradict that
  label for this build.
- A native reload duration or projectile lifetime of 0 means "use the default" or "no explicit
  limit". Writing a value there would change behavior rather than tune it, so those stay read-only.
- Scraped reload times match only approximately, because they include animation. Reload writes
  therefore require `allow_unverified_effect`.
- `WeaponReloadComponentData` and `WeaponWindUpComponentData` are added to the runtime profile.
  Every relied-on native table is proven byte-identical between the live snapshot and the pinned
  reference.

### Delivery-resolved support weapons

**MG-43 Machine Gun, M-105 Stalwart, MG-206 Heavy Machine Gun, and CQC-20 Breaching Hammer** are
now writable, with `identityStatus` `DELIVERY_RESOLVED`. A duplicate group is resolved only when
both of these hold:

1. The linked call-in stratagem's hellpod rack attaches exactly one candidate root.
2. That root alone has the scraped magazine values, and the other roots differ.

Every write re-proves live that the call-in payload is the rack and that the rack attaches the
delivered root. Other native roots with the same catalog name, such as the FRV gun or emplacement
variants, keep their own records and are not changed.

### Still blocked

| Weapon | Reason |
| --- | --- |
| EAT-17 Expendable Anti-Tank | Delivery is unique, but both roots are byte-identical in magazine and fire rate. |
| LAS-98 Laser Cannon | The delivered root's reload (5.0 s) conflicts with the scraped 3.65 s. |
| B/FLAM-80 Cremator | The scraped 500 capacity matches the Exosuit root, not the handheld weapon. |
| CQC-72 Entrenchment Tool | No call-in stratagem is linked. |

A known call-in relationship alone still never lifts a write block.

## Boosters

New domain: **`hd2.booster(name)`**, with the catalog **`sdk/BoosterAuthoringCapabilities.json`**.
See [booster authoring](../booster-authoring.md).

Boosters have no native record of their own. Their fields live on the records the native
`Booster` enum links to, and the type library references that enum from only two places.
Identity comes from the game's own UI template, which maps each native member name to a booster
icon; names are matched to enum values by type-library alias length. Seven boosters resolve to a
unique value. Eleven share a name length and stay candidate sets rather than being guessed.

| Booster | Target | Fields | Link |
| --- | --- | --- | --- |
| Armed Resupply Pods | `:deployed_entity()` | `weapon.fire_rate` (640), `magazine.capacity` (140) | Structural: Resupply stratagem booster entry → entity delta → resupply hellpod rack → turret entity. Re-proven live on every write. |
| Experimental Infusion | `:status_effect()` | `status.strength` (1.1), `status.duration` (10 s), `status.incoming_damage_scale` (0.9, new constant) | Unique exact fingerprint of both published effects (movement ×1.1, damage taken ×0.9). |

- **All booster writes require `allow_unverified_effect`.** No booster edit is gameplay-proven yet.
- **Experimental Infusion additionally requires `allow_shared`.** Game code applies its status
  effect; no weapon damage references it, but other code paths cannot be excluded.
- **Integrated Extinguishers** publishes its relationship but nothing is writable. It gates two
  avatar status susceptibilities through an override preset whose meaning is not proven.
- **Unsupported boosters stay blocked rather than guessed.** Effects applied only by game code
  have no data-backed value; each booster lists its reason. This covers reinforcement budget,
  extraction, radar, stamina, samples, and hellpod payloads.
- The turret's projectile is shared with player weapons, so it is not editable through the booster.

## API and SDK

- `hd2.booster(name)`, with `:describe()`, `:status_effect()`, and `:deployed_entity()`.
- New field constants: `hd2.fields.reload.duration`, `hd2.fields.windup.wind_up_seconds`,
  `hd2.fields.windup.wind_down_seconds`, `hd2.fields.projectile.lifetime`,
  `hd2.fields.projectile.penetration_slowdown`, and `hd2.fields.status.incoming_damage_scale`.
- Weapon patches and transactions accept `allow_unverified_effect` for fields that declare it.
- New example projects `ArmedResupplyTurret` and `CombatStimBoost`, both requiring 0.24.0. The
  ModTemplate now requires 0.24.0.

## Validation

- The support-weapon and booster snapshot validators resolve every field through the production
  chain proofs and apply it as a guarded no-op.
- The packaged-runtime validator applies 12 scenarios from the built runtime ZIP. New scenarios
  cover the support coverage and both booster targets, each with real overlay writes and
  re-application after a simulated reset.
